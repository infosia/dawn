> I realized that the complexity we introduced here is due to we mixed two things in a single patch:
> 1. The wrong validation rules, which inspector use immediate block size with trailing padding bytes to validate the immedaite size attribute.
> 2. An optimization, which we shrink the immediateMask based on internal-user defined immediates to "compress" the uploading size we do in API side.

**[src/dawn/native/Pipeline.h:130] (Round 8)** - @Stephen White (2026-02-26 14:21:04):
> Hi Shaobo! For the immediate size passed to Tint, I used ImmediateConstantMask::count() to count the number of actually-used immediate slots (including internal uses). It's "compressed", skipping any unused slots in the immediate data, matching what Tint will produce in the IR struct. I then round it up by 4 slots to match the widest possible alignment of members (e.g., vec4) in case that, e.g., one stage contains a vec4 and the other does not. Code here: https://source.chromium.org/chromium/chromium/src/+/main:third_party/dawn/src/dawn/native/opengl/ShaderModuleGL.cpp;l=438
> 
> Tint's decompose transform then maxes that length with the WGSL-computed struct size to determine the array length. This may produce an array that is larger than strictly required by one stage or the other, but that shouldn't be a problem. Code here: https://source.chromium.org/chromium/chromium/src/+/main:third_party/dawn/src/tint/lang/core/ir/transform/decompose_access.cc;l=183
> 
> Validation is left as-is, using the pipeline immediate size as computed by the front-end.

**[src/dawn/native/Pipeline.h:130] (Round 8)** - @Shaobo Yan (2026-02-24 08:35:44):
> I think it is great. Will use decompose transform.

**[src/dawn/native/Pipeline.h:130] (Round 8)** - @Shaobo Yan (2026-02-26 08:48:13):
> senorblanco@, I'm hitting an situation about this.
> Background: to remove trailing space in user immediate struct, we need to host two sizes. One is the user immediate block size without trailing space, we use this for validation. The other is the user immediate block size (with trailing padding). We need it because of internal immediates. We calculate internal immediates in API side and uplod the offset. PrepareImmediateData transform accept the offset and try to insert it into immediate blocks. The transform will check whether it has conflicts with other members. So we need the padding size to make the layout correct.
> 
> In metal, there is another problem due to the restriction describe in the comment.
> 
> In sync with cwallez@, it seems GL backend has similar issues (some attributes will be eliminated by driver and layout will be changed dynamically). So do you any suggestions on this case?
